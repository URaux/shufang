# 书房多人校对协作 — 研究与设计（2026-08-15）

> 结论先行：**用 isomorphic-git（纯 JS，npm 装进 webapp）做本地 git + GitHub 私有仓同步；每本书一个仓；协作走「建议文件」模式（一条建议 = 一个独立小文件），把冲突概率压到接近零；朋友不用注册 GitHub，发起人把一个仓级 token 打包成「邀请串」微信发过去就能加入。**
>
> 全文按六个研究问题逐个给结论，最后是总体架构、分阶段计划、放弃清单、风险清单。

---

## 问题一：git 从哪来

用户机器上没有 git，安装器刻意零依赖（Windows 不用 winget/git，更新走 codeload tarball）。三条路对比：

| | isomorphic-git（纯 JS） | 便携 git 二进制 | 自造简化版本管理 |
|---|---|---|---|
| 体积 | npm 包约 2MB，装进 webapp/node_modules | Windows 有 MinGit（zip 约 37MB，2026-08 仍活跃发布）；**Mac 没有等价物** | 0 新依赖 |
| Windows 兼容 | 好（跑在 Node 上，Node 的 fs 走 Unicode API） | 好 | 好 |
| Mac 兼容 | 好（同一份代码） | **不行**。Mac 上独立 git 二进制没有官方便携版：要么 Xcode 命令行工具（下载 1GB+、要用户点系统弹窗），要么 Homebrew（违反零依赖约束）。sourceforge 上的老 git-osx-installer 已停更多年 | 好 |
| 中文路径/文件名 | 好。git 树里按 UTF-8 字节存路径，Node fs 原生 Unicode，两端一致。（注：macOS 文件系统的 NFD 归一化只影响带音标的拉丁字母和韩文，**汉字没有分解形式，不受影响**——书房的文件名全是中文+数字，安全） | 好（现代 Git for Windows 默认 UTF-8） | 好 |
| 几十 MB 的 vault | 没问题。isomorphic-git 的短板是「巨型仓库解析 packfile 慢」，一本书几百个 markdown 文件、几十 MB，实测量级在秒级 | 最快 | 取决于自己写得多好 |
| 认证 | HTTP Basic，`onAuth` 回调里塞 GitHub token 即可，fine-grained PAT 直接可用 | git credential 配置，或把 token 拼进 URL | 自己实现 |
| 维护状态（查证于 2026-08-15） | **npm 最新 1.41.4，发布于 2026-08-13**，8 月一个月发了 5 个版本，GitHub 8.3k star，活跃 | Git for Windows 活跃（v2.55.x） | 全靠自己 |
| 已知坑 | ① 浅克隆（shallow clone）后 push 有 bug → **我们全量克隆，不受影响**；② 没有 rebase，merge 只做简单三方合并 → 设计上把合并需求消掉（见问题三）；③ 不支持 LFS → 不需要 | 双平台两套逻辑、spawn 子进程、PATH 管理 | 没有历史、没有 blame、朋友里懂技术的人无法用真 git 参与 |

**推荐：isomorphic-git。** 决定性理由就一条：**Mac 上根本没有零依赖的便携 git 二进制**，便携二进制路线在 Mac 端直接死掉。而 isomorphic-git 一份代码两端跑，产出的又是**标准 git 仓库**——懂技术的朋友可以直接 `git clone` 用真 git 参与，GitHub 网页上也能看历史。自造版本管理则违背了用户「尽量走 git」的明确意愿，而且把历史、回滚、审计全部重新发明一遍，不值。

顺带的免费好处：装了 isomorphic-git 之后，**每本书本地就有版本历史了**（哪怕不开协作）。译文改坏了能回滚，这本身就值回票价。

### 一个实施层面的坑（必须处理）

Windows 的「启动书房.bat」只在 `node_modules` **不存在**时才跑 `npm install`；`update.ps1` 更新时会把旧 `node_modules` 原样搬过来。所以**光在 package.json 里加依赖，老用户自动更新后会因缺包起不来**。解法（推荐后者）：

- 改启动器每次更新后都 `npm install` —— 但老用户的启动器/update.ps1 是安装时生成的，不随仓库更新，改了也到不了老用户手里；
- **server.js 启动时自愈**：`require.resolve('isomorphic-git')` 失败就自己 spawn 一次 `npm install` 再加载，失败则只是协作功能不可用，看书聊天照常。一段代码解决所有存量用户，且以后加任何依赖都受益。

## 问题二：仓库形态

### 每本书一个私有仓（推荐），不是每个 vault 一个仓

| | 每本书一仓 | 整个 vault 一仓 |
|---|---|---|
| 邀请粒度 | 只共享这一本书，A 组朋友读盖茨比、B 组朋友读别的，互不可见 | 邀请 = 交出整个书房，包括私人笔记和其他书 |
| 体积 | 一本书几十 MB，克隆快 | 随藏书量无限涨 |
| 版权 | 一本书泄了只泄一本 | 一锅端 |
| 实现 | 仓库根 = `Library/<书名>/`，`.git` 藏在书文件夹里，现有的 `/api/books`、阅读器完全无感 | 也可行但没优势 |

### 谁建仓、朋友怎么加入 —— 核心绕法：共享 fine-grained PAT

GitHub 账号对非程序员确实是门槛（英文界面、邮箱验证、2FA）。但注意：**只需要一个人过这道门槛**——发起人。朋友完全不需要 GitHub 账号，绕法如下：

1. **发起人**（通常是拍板人）注册 GitHub 账号——全流程只有这一个人做一次。书房 UI 给图文向导。
2. 发起人在书房界面点「共享这本书」，书房打开预填好的 `github.com/new`（仓名自动生成，Private 已勾上），发起人点一下 Create 即可。
   - 为什么不用 API 自动建仓：建仓需要 administration 权限的 token，而我们希望 token 权限最小化。让人点一下网页，换来 token 只需要 Contents 读写，划算。
3. 发起人创建一个 **fine-grained PAT**：只勾选这一个仓库、只给 Contents: Read and write 权限（书房给深链接直达 `github.com/settings/personal-access-tokens/new` + 截图指引）。有效期可选最长档或不过期（2026 年 GitHub 已放开 366 天上限；组织策略除外，个人账号可用）。
4. 书房把 `{仓库地址, token, 书名, 角色}` 打包 base64 成一个**邀请串**（形如 `SF1:xxxxx...`），发起人微信发给朋友。
5. 朋友在自己的书房里粘贴邀请串 → 自动克隆 → 书出现在书架上，填一个「署名」（显示名）就完事。**朋友全程没接触过 GitHub 三个字。**

所有人推送时用的都是同一个 token（认证身份 = 发起人），但 **git 的 commit author 是自由填写的**——每个人的提交署自己的显示名，历史里照样分得清谁干的。这不是权限模型上的洁癖方案，但对「几个朋友啃一本书」的信任模型完全够用（见问题六的风险讨论）。

放弃的替代方案：
- **每个朋友注册 GitHub + 正经 collaborator 邀请**：权限模型最正，但 N 个非程序员 × 注册流程 = 劝退。留作可选路径（懂技术的朋友可以走这条，用自己的账号 clone，体验完全兼容）。
- **发起人建 machine user / GitHub App**：更复杂，收益为零。

## 问题三：协作模型 —— 「建议文件」模式

三个候选：

| | 都推 master 直改译文 | 每人一个分支 + 合并 | **建议文件模式（推荐）** |
|---|---|---|---|
| 冲突概率 | 中。两人同时改同一章译文就冲突，而冲突恰恰集中在大家都在看的热门章节 | 低（写时不冲突），但**合并时全爆发**，且「分支」「合并」概念对非程序员无法翻译成人话 | **≈0**。每条建议是一个新建的独立文件，文件名全局唯一，git 合并新增文件永不冲突 |
| 非程序员心智 | 「别人把我的译文改了」——不可接受，没有审核环节 | 不可行 | 「我提意见 → 拍板人点采纳」——就是微信群里挑错的数字化，零学习成本 |
| 拍板环节 | 无 | 有（但形式是 PR，太重） | 有，且天然内建 |

**推荐：建议文件模式，单分支（master），所有人直接推。** 数据模型：

```
Library/<书名>/
  校对/
    03-第三章/
      20260815-1432-小王-a3f2.md     ← 一条建议一个文件
      20260815-1440-小李-9c01.md
  .协作/
    config.json                      ← 本书协作配置：角色表、显示名（可同步的部分）
```

建议文件用 markdown + YAML frontmatter（Obsidian 里人能直接读，代码也好解析，和 vault 的气质一致）：

```markdown
---
id: 20260815-1432-小王-a3f2
chapter: 译文/03-第三章.md
anchor: "盖茨比信奉那盏绿灯"        # 译文中被选中的原句（精确字符串锚点）
anchor_index: 1                     # 第几处出现（防重复句）
proposed: "盖茨比信仰的是那盏绿灯"
reason: "「信奉」搭配「灯」有点硬，原文 believed in 语气更执念"
author: 小王
created: 2026-08-15T14:32:00+08:00
status: open                        # open / accepted / rejected / stale
---
（可选的补充讨论，追加在正文里）
```

写入规则把「同文件双写」也基本消掉：
- 建议创建后，**作者**只在 status=open 时能改自己的文件（补充理由/撤回）；
- **拍板人**采纳/拒绝时把 status 和 decided_by/decided_at 写回同一文件；
- 唯一的双写窗口是「作者补充理由的同时拍板人正在拍板」——概率极低，且兜底策略处理（见问题五）。

**译文文件（`译文/*.md`）只有拍板人（的采纳动作）会改**，原书/梗概/摘要入库后只读，glossary 由拍板人维护——热点文件单写者，这是冲突≈0 的第二根支柱（第一根是按章分文件，仓库里已经天然如此）。

这个模型和你 PGM 校对页的数据模型是同构的：一条建议 = 选中原文 + 改成这样 + 为什么 + 署名。以后想把 PGM 站的读者反馈也接进来，格式都是现成的。

## 问题四：UI 融入

### 阅读器（拍板人和所有人）

- **行内高亮**：渲染译文时，server 端把每条 open 建议的 anchor 字符串在 HTML 里包上 `<mark data-suggestion-id>`（精确字符串匹配 + 第 N 处出现；匹配不到就标为 stale，不高亮）。读者看到译文里有淡黄色下划线的句子 = 有人提过意见。
- **侧栏「校对」区**：现有侧栏（书架/译文/原文/笔记/讨论）加一个「校对 (3)」分组，列出本书 open 建议；点击跳到对应章节并滚动到锚点。
- **建议卡片**：点高亮或侧栏条目，弹出卡片：`原句 → 建议改为 → 理由 → 署名·时间`。
  - 所有人可见「👍 附议」（追加到正文，追加是低冲突操作）；
  - **只有拍板人**看到「采纳」「不采纳」按钮（角色来自邀请串，存本地 config，UI 层控制——不是安全边界，是防误触）。
- **提建议**：读译文时选中一段文字 → 浮出「提个建议」→ 填「改成什么 + 为什么」两个框 → 落盘成建议文件。选区→锚点由前端取选中文本完成，零歧义。

### 采纳动作 = 确定性代码，不走 LLM

拍板人点「采纳」时，**server.js 用字符串替换直接改译文文件**（anchor → proposed），同一次 commit 提交译文修改 + 建议文件状态变更。这里刻意不让大脑（LLM）动手：采纳是个精确操作，不能引入任何改写的不确定性。anchor 找不到（译文后来又改过）→ 建议标 stale，提示「译文已变，让助手帮你重新对一下位置」。

### 聊天大脑（Claude Code）在协作里干什么

大脑不碰 git（同步是 server 的事，不让 LLM 摸版本控制），但它读写 vault 文件，所以建议文件对它就是普通 markdown。给 book-translator skill 加一节「校对」流程后，自然获得这些能力：

- 「帮我看看小王这条建议有没有道理」→ 读建议 + 原文 + 译文上下文，给评审意见（对照原文这是协作里最值钱的一环：非程序员拍板人未必读得动原文，大脑替他核对）；
- 「有哪些新建议？」「把小李的建议都采纳了」→ 自然语言批量操作（采纳仍走 server 的确定性通道，大脑只是发起）；
- 「按大家的意见把第三章重新顺一遍」→ 深度改稿后由 sync 引擎正常提交。

## 问题五：同步时机

**总原则：用户永远不知道「同步」这个词的存在。** 界面上唯一的痕迹是右上角一个小圆点（绿=已同步 / 黄=有待上传 / 灰=离线）和「刚刚有 2 条新建议」这类人话通知。

| 时机 | 动作 |
|---|---|
| 启动时 | 对每本共享书：fetch + 合并远端（等价 pull）。失败（断网）静默跳过，照常起 |
| 本地有改动后 | 文件监听（chokidar 或轮询 mtime）→ 防抖 30 秒 → add-all + commit（author=本机署名）→ fetch → 合并 → push |
| 后台 | 每 2 分钟 fetch 一次；远端有新东西就合并 + SSE 通知前端刷新（「小王提了条新建议」） |
| 断网 | 一切照常（本地 commit 照打），状态点变灰；网络恢复后下一个周期自动补推。git 天生就是离线优先的，这是选 git 的最大红利 |
| push 被拒（远端更新了） | fetch → 合并 → 重推，循环最多 3 次（标准 git 工作流，代码自动做） |

### 兜底：真的撞了怎么办

建议文件模式下合并冲突理论上只剩一种来源：**同一个文件被两端同时改**（作者补充理由 vs 拍板人拍板；或两个拍板人同时改同一章译文）。兜底策略——**「远端赢 + 本地备份 + 人话通知」**：

1. 冲突文件的本地版本复制为 `xxx.冲突备份-<日期>.md`（不进 git，本地留档）；
2. 采用远端版本，合并继续，同步不中断；
3. 前端通知：「你和小王同时改了『第三章』的同一处，他的先到就先生效了。你的版本我留了底，点这里让助手帮你把两边合起来。」→ 大脑做语义级合并，这是 LLM 真正擅长、传统 git 又真正不擅长的事。

绝不出现 conflict marker、绝不出现「resolve / rebase」字样，同步永远不会因冲突卡死。

## 问题六：安全

| 事项 | 方案 |
|---|---|
| token 存哪 | `~/.shufang/config.json`，与 DeepSeek key 同一先例、同一保护级别。**绝不放进 vault**（vault 会被同步出去）。每本书记录：仓库地址、token、角色、署名 |
| 书的内容不公开 | 私有仓（GitHub 免费账号私有仓不限量）。建仓向导里 Private 预勾选 + 建仓后 server 调 API 校验 `private: true`，不是私有就红字警告。版权书永不进公开仓是硬规则 |
| token 权限半径 | fine-grained PAT：单仓 + 仅 Contents 读写。泄漏最坏后果 = 这一个私有仓的内容被读走/改坏（改坏可用 git 历史回滚）。**不能**动发起人其他仓库、不能删仓、不能改设置 |
| 邀请串走微信 | 明文风险如实接受：威胁模型是「几个朋友读书」，不是对抗性环境。缓解：文档写明「别发到大群」；token 可随时在 GitHub 撤销重发（书房提供「换钥匙」按钮：撤旧 token 指引 + 重新生成邀请串） |
| token 过期 | fine-grained PAT 可设不过期；若用户设了期限，push 401 时前端人话提示「共享钥匙过期了，找发起人要个新的邀请串」，本地功能不受影响 |
| 朋友作恶/误删 | 共享 token 意味着技术上人人可写一切。防御 = git 历史（任何破坏可回滚）+ 熟人信任。UI 上非拍板人看不到危险按钮，防误触足矣 |

## 总体架构

```
 发起人的电脑                                朋友的电脑
┌────────────────────────┐                ┌────────────────────────┐
│ 书房 webapp (server.js) │                │ 书房 webapp (server.js) │
│  ├─ 阅读器+建议卡片 UI    │                │  ├─ 阅读器+建议卡片 UI    │
│  ├─ 聊天大脑 (claude -p) │                │  ├─ 聊天大脑 (claude -p) │
│  └─ sync.js (新模块)     │                │  └─ sync.js (新模块)     │
│      isomorphic-git      │                │      isomorphic-git      │
│        │                 │                │        │                 │
│  Library/盖茨比/  ← .git │                │  Library/盖茨比/  ← .git │
│    ├─ 00-原书/           │   HTTPS+PAT    │    （克隆自远端）          │
│    ├─ 译文/     ←只拍板人改│      ▲         │                        │
│    ├─ 校对/     ←建议文件 │      │         │                        │
│    └─ glossary.md        │      ▼         │                        │
└────────────────────────┘   ┌──────────┐  └────────────┬───────────┘
                             │ GitHub    │◄──────────────┘
                             │ 私有仓     │    HTTPS + 同一个 PAT
                             │ (每书一仓) │    (commit author 各署各名)
                             └──────────┘
```

要点：两端软件完全相同（没有服务器/客户端之分），角色差异只是本地 config 里一个字段 + UI 显隐；GitHub 只当哑存储用，不用它的 PR/Issue/Review 任何功能。

## 分阶段实施

### 第一阶段（最小可用，先让「三个人啃一本书」跑通）

1. `webapp/sync.js`：isomorphic-git 封装（init/clone/commit-all/fetch/merge/push + 「远端赢+备份」兜底）+ server.js 启动时依赖自愈（npm install 补装）；
2. 每本书入库时静默 `git init` + 本地自动 commit（**所有用户白得版本历史，与协作无关也值得**）;
3. 共享向导：GitHub 注册/建仓/PAT 三步图文页 + 生成邀请串 + 粘贴邀请串加入；
4. 建议文件读写 API + 侧栏「校对」列表 + 建议卡片（提/附议/采纳/拒绝，采纳=server 字符串替换）；
5. 同步：启动拉、改后防抖推、2 分钟轮询、断网静默。

不做：行内高亮（侧栏列表已可用）、大脑评审、冲突语义合并——第一阶段冲突直接「远端赢+备份+通知」，让助手合并的入口后补。

**验收场景**：A 装好共享一本书 → B、C 粘邀请串各自看到书 → B 对第三章提两条建议 → A 这边 2 分钟内弹通知，点采纳 → 译文更新，B、C 侧自动出现新译文和「已采纳」状态。全程无人见过 git 一词。

### 第二阶段（体验完整）

行内高亮 + 锚点跳转；skill 加「校对」流程（评审建议/批量采纳/语义合并两个版本）；stale 建议的助手重定位；「换钥匙」token 轮换按钮；同步状态点和通知打磨。

### 第三阶段（按需）

glossary 建议化（译名争议也走建议流）；建议下的讨论线程；多拍板人；Gitee 备选远端（应对 GitHub 连通性，见风险）；导出「校对记录」成一页致谢/修订说明。

## 设计上放弃了什么、为什么

- **便携 git 二进制** —— Mac 上不存在零依赖便携版，跨平台即死；且 37MB 下载对着几十 MB 的 markdown 仓库是杀鸡用牛刀。
- **自造版本管理 / 纯 GitHub Contents API 同步** —— 违背用户「尽量走 git」的意愿；重新发明历史/回滚/离线队列；懂技术的朋友无法用真 git 参与。Contents API 保留为将来某个「无 token 只读分享」功能的备选。
- **每人注册 GitHub + 正经 collaborator** —— N 个非程序员的注册流程是最大流失点。留作兼容路径，不作主路径。
- **分支/PR 模型** —— 「分支」「合并请求」无法翻译成非程序员的心智模型；单分支 + 建议文件在这个规模（个位数协作者、按章分文件）下冲突概率已≈0，PR 的收益为零、成本无穷大。
- **直改译文（无拍板环节）** —— 「别人动了我的译文」违背需求里明确的「有人拍板合并」；且把冲突集中到热点文件。
- **让 LLM 执行采纳/合并/git 操作** —— 采纳必须逐字精确；git 状态机不能交给概率模型。LLM 只做它擅长的：评审建议、语义合并两个人类版本。
- **端到端加密邀请串** —— 熟人微信场景下是安全剧场，成本换不来实质收益；用「小半径 token + 可撤销」代替。
- **实时协同编辑（CRDT/OT 类）** —— 校对是异步慢节奏活动，实时性无需求，复杂度天壤之别。

## 风险清单

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **GitHub 在大陆连通性**（用户群在国内，github.com 的 git-over-HTTPS 时好时坏） | 同步慢/失败 | 同步全程后台静默重试，失败不影响本地使用（离线优先天生免疫）；安装器已有「挂梯子」话术先例；第三阶段留 Gitee 备选（同为标准 git smart-HTTP，isomorphic-git 无缝；Gitee 免费版有仓库成员数限制，但共享 token 模式根本不加成员，不受限） |
| 2 | **Windows 存量用户自动更新后缺新依赖**（启动器只在 node_modules 不存在时 npm install，update.ps1 不装依赖） | 更新后起不来 | server.js 启动自愈：探测缺包→自动补装→失败则仅禁用协作功能。**这条是实施红线，必须先做** |
| 3 | 共享 token 经微信泄漏 | 单个私有仓内容泄漏/被改 | 仓级最小权限、可撤销、「换钥匙」按钮、文档告知别发大群 |
| 4 | token 过期/被误撤销 | 同步静默失败 | push 401 → 前端人话提示 + 重新邀请流程；本地一切照常 |
| 5 | 单文件 >100MB 触 GitHub 硬限（超大 epub/pdf 原始文件） | push 被拒 | 共享初始化时检查 `原始文件.*`，>50MB 自动写进 `.gitignore` 并告知「原始文件太大没上传，不影响朋友看译文」 |
| 6 | isomorphic-git 合并遇到诡异边角（它的 merge 比原生 git 简单） | 同步卡住 | 写入模式已把并发同文件改动压到≈0；任何 merge 异常一律降级到「远端赢+本地备份」，同步永不中断 |
| 7 | 两个拍板人同时采纳不同建议改同一章 | 一方采纳结果被覆盖 | 第一阶段限一个拍板人；多拍板人到第三阶段，且备份+助手合并兜底 |
| 8 | anchor 字符串因译文重译而失配 | 建议变僵尸 | 标 stale 不高亮，助手重定位（第二阶段） |
| 9 | 朋友的电脑时钟不准导致建议 ID 撞名 | 覆盖他人建议 | ID 含 4 位随机后缀，撞名概率可忽略 |
| 10 | 非中文文件名（韩文/带音标）在 Mac 上的 NFD 归一化差异 | 幽灵改动 | 书房命名规范本就是中文+数字；skill 已规定书名「不带特殊字符」，维持即可 |
